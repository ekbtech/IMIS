# Hospital system requirements coverage

This matrix compares the user-provided hospital-system requirements with the code currently present in this repository. It is a delivery-status baseline, not a claim of operational readiness, regulatory compliance, clinical approval, or certification.

## Status definitions

- **Partial**: a bounded foundation exists, but significant requested capabilities are absent.
- **Scaffold only**: schema/API foundations exist but do not implement an operational department workflow.
- **Not implemented**: no meaningful product workflow is present.
- **Approval-dependent**: implementation or activation requires facility policy, clinical governance, legal review, or verified external specifications.

## Cross-cutting controls

Validation, timestamps, responsible-user attribution, backend permission enforcement, transactions, password hashing, MFA, encryption, and audit events exist in selected workflows. Department workspace listing and reading is department-assignment scoped, but most existing patient/clinical APIs still use permission and facility checks rather than department-level authorization. Maintenance requests and equipment register entries are visible only through the user's assigned departments. This is not yet a complete control set: the facility role matrix and SOPs are unapproved, audit review and sensitive-record controls are incomplete, retention/disposal policy is unapproved, and there is no complete concurrency/resilience, certification-evidence, or production-readiness validation across all requested modules.

## Delivery gates and sequence

The requested system is a multi-module programme; a department catalogue or passing unit test cannot satisfy it. Implement each bounded workflow end-to-end with schema, server-side authorization, UI, audit, failure handling, and MySQL-backed tests before calling that workflow complete.

1. **Facility foundation:** confirm facility identity/licensed services, department/resource taxonomy, named role matrix, care-team and sensitive-record rules, and retention schedule. Local finance is included in the requested later scope; external government interfaces remain deferred pending current official specifications.
2. **Core clinical continuity:** complete patient profile/contact and appointment/referral flows; add governed diagnosis, allergy, orders, and notes only against approved terminology, protocols, and authorization rules.
3. **Diagnostics:** approved catalog and order → specimen/exam → processing → result → verification/release → clinician review, with critical-result acknowledgement and audit.
4. **Inpatient and maternity:** approved ward/bed inventory, admission, transfer, occupancy constraints, nursing documentation, discharge and follow-up; separately validate maternity/newborn workflows.
5. **Pharmacy and inventory:** item catalog, stock ledger and traceability first, then prescription validation, FEFO dispensing, controlled-stock and recall/expiry processes.
6. **Procurement and asset lifecycle:** approved procurement policy and non-hardcoded rule configuration, requisition-to-GRN lifecycle, asset register, maintenance and approved disposal.
7. **Local finance and HR:** local finance is included in the requested scope, but implementation still requires approved accounting/payroll policies and separation of duties. External government interfaces require current official specifications and authorized access.
8. **Support services, reporting and evidence:** implement each selected service, report permissions/export controls, audit review, backup/restore, retention and deployment evidence.

No financial, government, diagnostic, inpatient, triage, or other clinically significant feature should be activated merely because a schema, demo setting, or department name exists. Validate workflows with authorized synthetic data and obtain the accountable facility approvals before any operational use.

## Delivery update (2026-10-23)

Migration `020` adds six facility-scoped divisions and associates departments with a division. It seeds the 60 requested department catalogue entries while reusing existing facility department records for recognized legacy codes; additional pre-existing departments are retained and assigned to a division. Authorized administrators can create, edit, reorder and deactivate divisions through the organization administration screen, and can reassign departments between active divisions. Deactivation is blocked while active departments remain assigned. The dashboard and department sidebar now use this division structure; staff only see divisions with assigned departments, while administrators can see empty active divisions. Division membership does not grant permissions, create mandatory division heads, activate services, or define operational approval authority.

The catalogue is an organizational foundation, not implementation of the requested department roles, responsibilities, forms, workflow routing, operational dashboards or reports. Those remain to be implemented in validated, department-specific slices using facility-approved procedures and permissions. The local development database has applied migration `020`; verification found six divisions and no unassigned department rows.
